# 性能测试

本文档说明 swanix 的性能测试方法、测试项目与实测结果，记录转发路径的优化，并给出由结果得出的配置建议。

## 1. 测试性质与适用范围

* 测试在 Linux 网络命名空间中进行：LAN 客户端、两个运营商（ISP）与路由器各占一个命名空间，相互以 veth 连接，所有命名空间共用同一内核与同一组 CPU。
  负载发生器、服务端、路由器转发路径与 swanix 守护进程竞争同一组 CPU。
* **绝对数值反映测试机器的处理能力，不代表路由器硬件的性能**；结论以同一次运行中的成对比较为准。
* 同一次运行中先后测量的两个阶段之间，机器状态的漂移可达 10%，超过待测效应。因此每项比较均采用**成对交替**方式：两种配置按 A B、B A、A B …
  交替运行，报告各自的中位数以及逐轮比值（B/A）的中位数。
* 测试结果不作为 CI 的通过条件。功能正确性（无连接失败、无下载中断、正确收敛）在测试中断言；性能数值仅作记录。
* 尚未在真实路由器硬件上进行性能测试。

## 2. 测试工具与项目

| 项目 | 实现 | 内容 |
|---|---|---|
| 负载工具 | `ci/test/perf/perfload` | 服务端：返回标识线路的 banner，按请求持续发送数据。连接测试：多并发「建立连接—读取 banner—复位关闭」循环，报告连接速率、延迟分位数与各线路分布。吞吐测试：多流并行下载，报告总吞吐与各线路数据量。 |
| 数据路径 | `TestPerfDataPath`（`cmd/swanix/e2e_perf_test.go`） | 三组成对比较：同一路径上无 swanix 与有 swanix（swanix 自身开销）；内核 ECMP 双线路（无 swanix）与 swanix 双线路均衡；按连接分配与源+目的粘滞（100 个客户端）。随后测量两类故障的收敛时间。每组比较运行 `SWANIX_PERF_ROUNDS` 轮（默认 3）。 |
| 权重更新 | `TestPerfWeightUpdatesUnderLoad`（`experimental/multiwan/kernel/perf_test.go`） | 在新建连接与持续下载的负载下执行 100 次权重更新（每次一个 nft 原子批处理）与 10 次完整重新应用，记录耗时；任何连接失败或下载中断均判为测试失败。 |
| Full 代理路径 | `TestPerfFullTUN`（`cmd/swanix/e2e_perf_full_test.go`） | 同一负载分别经内核路径（代理关闭）与 TUN + `wan_policy`（代理开启）转发，记录守护进程 CPU 时间。TUN 协议栈、MTU 与构建标签可选，默认 `gvisor`、MTU 1500、`with_gvisor`。 |
| 控制面基准 | `go test -bench` | 调度计算、nft 规则生成、路由计划生成、Full 版逐连接线路选择（并发）。 |

运行方式：

```sh
# 控制面基准
go test -run '^$' -bench . ./experimental/multiwan/scheduler ./experimental/multiwan/kernel ./experimental/multiwan/engine
# 数据路径、权重更新、Full 代理路径（需要 root，在一次性网络命名空间中运行）
sudo env "PATH=$PATH" SWANIX_PERF=1 SWANIX_PERF_ROUNDS=5 SWANIX_PERF_REPORT=datapath.json \
     ci/test/netns.sh -tags mw_lite ./cmd/swanix -run TestPerfDataPath -timeout 50m -v
sudo env "PATH=$PATH" SWANIX_PERF=1 ci/test/netns.sh ./experimental/multiwan/kernel -run TestPerfWeightUpdatesUnderLoad -v
sudo env "PATH=$PATH" SWANIX_PERF=1 ci/test/netns.sh ./cmd/swanix -run TestPerfFullTUN -timeout 30m -v
```

GitHub Actions 中的 `perf` 工作流（手动触发，可指定轮数）执行上述全部测试，在运行摘要中列出结果，并上传 `perf-report` 产物（JSON 与日志）。

健康检测参数：`interval 1`、`timeout 1`、`down_rounds 2`、`up_rounds 2`。连接测试 32 并发、每轮 8 秒；吞吐测试 8 流、每轮 8 秒；每组比较 5 轮。

## 4. 转发路径优化

### 4.1 改动

优化前，已建立连接的每个转发报文都要依次经过：每条线路一次接口集合查找、一次 FIB 路由查找（`fib daddr type local`）、两次旁路集合查找，
以及三次 ct mark 比较。这些判断只在连接建立时有意义：线路选择及本机、旁路地址的排除均只在首包执行一次，结果保存在 ct mark 中。

优化后的规则结构：

* `prerouting` 仅对 `ct state new` 跳转至 `prerouting_new`，在其中完成入站识别、本机与旁路排除、线路选择；`output` 链同样拆分为 `output_new`。
* 其余每个报文只执行一次以 `ct direction . ct mark & (线路 ID | 入站位)` 为键的映射查找，将连接的线路写入报文 mark。
  映射中不存在的键（未分配线路的连接、LAN 连接的回复方向、入站连接的原方向）直接放行，不作标记。

同时修正了粘滞记录的超时语义：记录在每个新连接时刷新（`update`），在客户端最后一次新建连接后 `affinity_timeout` 秒过期；
此前使用 `add`，活跃客户端会在 `affinity_timeout` 后被重新分配线路。

### 4.2 效果（环境 A，同一会话，5 轮中位数）

| 场景（相对无 swanix 的同路径基线） | 优化前 | 优化后 |
|---|---|---|
| 单条可用线路：连接速率 | −5.6% | −0.3% |
| 单条可用线路：吞吐 | −5.3% | −0.1% |
| 单条可用线路：延迟 p50 | 1.60 ms（基线 1.54 ms） | 1.47 ms（基线 1.47 ms） |
| 两条线路均衡：吞吐 | 20.19 Gbit/s | 22.11 Gbit/s |
| 源+目的粘滞（100 个客户端）：连接速率 | −26.9% | −21.6% |

该表为同一会话内先后两次运行的对比（每次运行内部为顺序测量），用于说明改动方向；严格的开销数值以第 5、6 节的成对比较为准。

## 5. 结果（环境 A）

### 5.1 数据路径（Lite，成对比较，5 轮）

| 比较 | A：中位数 | B：中位数 | 成对变化（B 相对 A） |
|---|---|---|---|
| swanix 自身开销：无 swanix（A）与 swanix 单条可用线路（B），同一路径 | 18 813 个/秒，23.09 Gbit/s，p50 1.45 ms | 17 660 个/秒，22.93 Gbit/s，p50 1.56 ms | 连接速率 −1.8%，吞吐 −0.8% |
| 双线路：内核 ECMP，无 swanix（A）与 swanix 均衡（B） | 14 885 个/秒，21.75 Gbit/s | 15 481 个/秒，21.44 Gbit/s | 连接速率 +2.2%，吞吐 −5.3% |
| 粘滞：按连接分配（A）与源+目的粘滞（B），100 个客户端 | 14 680 个/秒，20.07 Gbit/s | 13 583 个/秒，20.75 Gbit/s | 连接速率 −2.0%，吞吐 +6.7% |

* 全部轮次中连接失败数为 0。双线路时两条线路的连接数为 58 866 : 58 688。
* 守护进程每轮（16 秒负载）CPU 时间约 0.04 秒，不在数据路径中。
* 双线路场景的连接速率低于单线路，内核 ECMP 亦然，原因是两条转发路径与两个服务端进程的额外成本，与 swanix 无关。

### 5.2 故障收敛

收敛时间指从故障发生至一批新连接全部无错误且全部经 wan1 建立的时间。线路被判定为故障时，其份额在同一时刻降为 0。

| 故障类型 | 判定为 `down` | 新连接收敛（多次运行范围） | 决定因素 |
|---|---|---|---|
| 上游中断（丢弃全部报文） | 3.1–4.3 s | 3.4–5.6 s | 探测参数：首轮失败的相位 + `down_rounds` 轮 × (`interval` 或 `timeout`) |
| 链路断开（netifd 报告接口 down） | 0.5–1.1 s | 0.9–1.4 s | netlink 事件去抖（0.5 s）与接口状态读取，不依赖探测 |

### 5.3 权重更新（内核层，负载下）

| 操作 | p50 | p99 | 最大 |
|---|---|---|---|
| 权重更新（一个 nft 原子批处理），100 次 | 29.5 ms | 50.0 ms | 50.0 ms |
| 完整重新应用（nft 表、规则与路由），10 次 | 131.8 ms | — | 147.8 ms |

更新期间约 6 万次新建连接无一失败，4 路下载均未中断（最慢一路 3.6 Gbit/s）。耗时主要来自 `nft` 进程启动。

| 路径 | 连接速率（个/秒） | 延迟 p50 / p99（ms） | 吞吐（Gbit/s） | 守护进程 CPU（连接测试，8 秒） |

## 7. 结论与建议

1. **swanix 在内核路径上的开销很小。** 成对比较中，单线路场景相对无 swanix 的同一路径：4 vCPU 环境连接速率 −1.8%、吞吐 −0.8%；
   2 vCPU 环境均为 −5.4%。双线路均衡与内核 ECMP 相差 −5% 至 +2%。延迟中位数增加约 0.1 ms。
2. **剩余开销的来源。** 每个已建立连接的报文需执行一次 mark 映射查找；另外，带 mark 的报文在策略路由中先经过 `lookup main suppress_prefixlength 0`
   规则（使直连与 VPN 路由优先于线路默认路由），再查找线路路由表，即每个报文两次路由表查找，而直接路由为一次。后者是正确性所需，予以保留。
3. **均衡与粘滞的成本可以忽略。** 粘滞相对按连接分配的成对变化在 ±3% 以内（测量噪声范围内）。
4. **守护进程不承担转发。** 无论负载大小，守护进程 CPU 占用可以忽略，内存约 10 MiB（Lite）。
5. **故障收敛由探测参数决定。** 上游中断约 3–6 秒收敛（`interval 1`、`down_rounds 2`、`timeout 1`）；链路断开在 1.5 秒内收敛。
   缩短收敛时间应调小 `interval` 与 `down_rounds`，代价为更多探测流量与更高的误判概率。
6. **权重更新对业务无影响。** 每次更新为一个原子批处理，耗时数十毫秒，期间无连接失败、无下载中断。
7. **需要最高转发性能时，启用软件流量卸载。** 已卸载的连接绕过上述全部规则与策略路由，且沿用首包选定的线路（见使用指南 8.11）。
8. **代理路径成本高，应仅用于需要代理的流量。** TUN 接管全部 LAN 流量时，连接速率约为内核路径的 1/3 至 1/5，吞吐为其 3%–7%。
   需要使用 TUN 时，建议使用 `"stack": "gvisor"` 与 `"mtu": 1500`；不需要代理的流量应保留在内核路径（使用显式代理入站如 SOCKS，或通过路由排除）。
